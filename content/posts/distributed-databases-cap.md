Когда данные не помещаются на один сервер или нужна отказоустойчивость, СУБД делают распределённой. Это порождает фундаментальные компромиссы, которые описывает CAP-теорема.

## Распределённые СУБД

Данные разносят по узлам двумя способами:

- **Шардирование (партиционирование)** — разные части данных на разных узлах (масштаб по объёму и нагрузке).
- **Репликация** — копии одних данных на нескольких узлах (отказоустойчивость и чтение ближе к клиенту).

Репликация ставит вопрос: что делать, если между копиями порвалась связь?

## CAP-теорема

Утверждает, что распределённая система не может одновременно гарантировать все три свойства:

- **C (Consistency)** — все узлы видят одни и те же актуальные данные;
- **A (Availability)** — каждый запрос получает ответ (не ошибку);
- **P (Partition tolerance)** — система продолжает работать при **разрыве сети** между узлами.

Ключевое понимание: в реальной распределённой системе сетевые разрывы **неизбежны**, поэтому `P` обязателен. Значит, при разделении реально выбирают между **C и A**:

- **CP** — при разрыве жертвуют доступностью ради согласованности (лучше ошибка, чем устаревшие данные);
- **AP** — при разрыве жертвуют согласованностью ради доступности (ответить хоть чем-то, синхронизироваться позже).
- **CA** без `P` возможна лишь в системе без разделений — по сути, на одном узле / классические РСУБД.

## ACID против BASE

Классические РСУБД дают **ACID** (Atomicity, Consistency, Isolation, Durability) — строгие гарантии транзакций. Многие распределённые NoSQL-системы выбирают **BASE**: **B**asically **A**vailable, **S**oft state, **E**ventual consistency — доступность важнее, а согласованность достигается **со временем** (eventual). Это плата за масштаб и отказоустойчивость.

## Примеры по классам

- **CP:** HBase, MongoDB (в строгой конфигурации), etcd/ZooKeeper.
- **AP:** Cassandra, DynamoDB, Riak — приоритет доступности с eventual consistency.
- **CA (без разделений):** классические одноузловые РСУБД (PostgreSQL, MySQL) в неразделённом развёртывании.
